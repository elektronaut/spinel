Fixes #4985.

`codegen_program` in `src/codegen.c` skipped the extern for any `ffi_func` with an `ffi_callback` parameter. It assumed a system header declares such a function (`qsort`, `bsearch`), and that our own prototype, whose array and pointer specs may not match the header's `void *` parameters, would conflict with it under gcc. The call site in `src/codegen_call.c` then called the bare symbol name, casting `str`, `int_array` and `float_array` arguments to `(void *)` so they converted cleanly to the header's parameter types. For a function no included header declares, such as `lfind` or `lsearch` from `<search.h>`, the call had no prototype at all. C falls back to an implicit declaration returning `int`, so a `:ptr` result is truncated to 32 bits. Heap pointers on x86-64 sit above 4 GB, so a real returned address comes back wrong, while NULL survives the truncation. gcc 13 only warns; gcc 14 and later and clang reject the implicit declaration. The conflict the skip worked around no longer exists: every other `ffi_func` is already declared under a private name (`sp_ffi_f<N>_<sym>`) bound to the real symbol with an `__asm__` label, and a private name can't clash with a header's declaration.

Callback-taking functions now get the same private-name extern as every other `ffi_func`. A callback parameter is typed as the trampoline's own function pointer type, `ret (*)(ffi_cb_arg_ctype...)` built from the callback's spec, so `&__sp_ffi_cb_N` matches it exactly. The call always goes through that extern, and the `(void *)` argument casts that existed only for bare header calls are gone. What stays the same: a variadic function with no fixed arguments still has no extern and is still called through a cast to a variadic function pointer, since there is no prototype to write for it. A callback-taking function is still never made a `blocking:` call, because the callback may run Ruby (the old `hdr_call` flag becomes `takes_cb` and now does only that). Because the parameter types come from the callback's own spec and the name is private, a header whose prototype spells the parameters differently (`Uint8 *` in SDL2, for example) can't conflict with it.

Tests: `test/ffi_callback_no_header.rb` is the original shape, `lfind` on an empty array with a `:ptr` result compared to `nil`. It prints `true` on master too, since NULL survives the truncation, and only shows the bug as a compiler warning. `test/ffi_callback_no_header_ptr.rb` is the issue's reproducer extended: `lsearch` and `lfind` returning a real heap pointer, plus NULL results. On master it prints `true false false true` with four `-Wint-to-pointer-cast` warnings; with this change it prints four `true` and no warnings. Every test using `ffi_func` or `ffi_callback` (37, including the two new ones) also passes under `--cc=clang` (clang 18), where master fails the pointer test. The `.expected` files hold Spinel's correct output, since CRuby has no `ffi_callback`. `make gate` is clean apart from the two known sandbox failures.
