Fixes #4983.

Ruby matches the elements of `Array#-`, `|`, `&` and `intersect?` (and `difference`, `union`, `intersection`) by `hash`/`eql?`, so `2` and `2.0` are different elements. In `lib/spinel_rt.h`, `sp_PolyArray_difference`, `sp_PolyArray_union`, `sp_PolyArray_intersect` and `sp_PolyArray_intersect_p` decided membership with `sp_PolyArray_include_val`, which compared with `sp_poly_eq`, i.e. `==` with Integer/Float coercion. So `[1, 2, "y"] - [2.0]` removed the `2`, `| [2.0]` dropped the `2.0` as a duplicate, and `& [2.0]` kept the `2`. An Integer array against a Float array goes through the same PolyArray helpers and was wrong the same way in both directions, and so were nested arrays (`[[1, 2]] - [[1, 2.0]]` came back empty), because `==` on arrays recurses with `==`.

`sp_PolyArray_include_val` is replaced by `sp_PolyArray_include_eql`, which compares with the existing `sp_poly_eql`: like `sp_poly_eq` but an Integer is never `eql?` to a Float, and arrays recurse element by element with `eql?`. The four set-operation helpers use it. `sp_PolyArray_include_val` had no other callers, so nothing else changes: `include?`, `index` and `count` keep `==`, as in Ruby. For values that aren't a mixed Integer/Float pair, `sp_poly_eql` answers the same as `sp_poly_eq`, so set operations on other element types are unaffected. `uniq`, `tally`, `group_by` and Hash keys mixing Integer and Float (`h[2]` vs `h[2.0]`, `key?`, `merge`) were checked and were already correct on master.

Tests: `test/poly_array_set_eql.rb` contains the issue's reproducer and also covers the method forms (`difference`, `union`, `intersection`, `intersect?`), an Integer array against a Float array in both directions, nested arrays with `-`, `&` and `|`, and that `include?` still uses `==` while `uniq` keeps `2` and `2.0` apart. It fails on master and matches CRuby 4.0 with this change. `make gate` is clean apart from the two known failures, `pkg.tmpdir.tmpdir_expand_usable` and `socket_ipv6_and_class_methods`.
