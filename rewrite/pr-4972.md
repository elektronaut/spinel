Fixes #4971.

Top-level method lookup always answered the first definition of a name. `comp_method_index_direct` in `src/compiler.c` scanned the scopes in ascending order, and `sm_build` built the frozen top-level index in descending order so that the lowest scope index ended at the head of its bucket. So every call to a redefined top-level method bound to the first `def`: a later definition with another arity had its calls refused with an `ArgumentError`, and one with the same signature produced two C functions with the same name. `scope_is_shadowed` only handled class methods, so nothing kept the earlier top-level definition from being emitted. `multi_return_elem_types` in `src/analyze_pass.c` had its own first-match scan as well. Making the lookup plainly last-wins isn't CRuby either: a call that runs between the two definitions reaches the first one, and `test/builtins_take_drop_while.rb` depends on that (it calls `tw { }` between `def tw(&b)` and `def tw(a)`).

A new pass, `rename_redefined_toplevel_defs` in `src/analyze.c`, runs before scopes are built. When a top-level `def` without a receiver is redefined by a later top-level `def`, the earlier one gets a private name, `<name>__redef<N>`, and the receiverless calls in the top-level statements between the two definitions, including the blocks in those statements, are renamed to match. The walk doesn't go into def, class or module bodies, because they run later or with another self. The last definition keeps the name, so method bodies and later calls reach it. For a redefinition the pass can't place, such as a `def` inside an `if`, top-level lookup is now last-wins in both `comp_method_index_direct` and the frozen index, like a class's, and `scope_is_shadowed` treats an earlier top-level `def` as shadowed by a later one, so it isn't emitted. `multi_return_elem_types` now uses `comp_method_index`. Programs that don't redefine a top-level method are unaffected: the pass renames nothing, and a name with one definition resolves to the same scope either way. Class methods were already last-wins and are unchanged.

Tests: `test/toplevel_def_redefined.rb` contains both of the issue's reproducers. It also covers a redefinition with an added optional parameter, a redefinition that changes the return type, a method body and a class method calling the redefined method (both reach the last definition), a redefinition inside a class, calls and a block between two definitions (they reach the first one while a method body reaches the second), and a predicate name (`q?`). It fails on master and matches CRuby 4.0 with this change. `make gate` is clean apart from the two known failures, `pkg.tmpdir.tmpdir_expand_usable` and `socket_ipv6_and_class_methods`.

Not covered: a top-level lambda or proc that calls the method and is invoked after the redefinition still reaches the earlier definition, because the pass treats every block as running where it is written. `method(:name)` and `send(:name)` between the definitions aren't renamed. A `def` inside a conditional resolves to the last definition, where CRuby depends on which branch ran. `__method__` inside an earlier definition returns the private name.
