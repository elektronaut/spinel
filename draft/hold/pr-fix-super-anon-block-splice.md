title: super(&) into a yielding ancestor splices the caller's block

Fixes #N.

A yielding parent method has no C function of its own, so a `super` into it is spliced by `emit_super_inline`, which inlines the parent's body and needs to know which block to splice into its yields. When the method calling `super` is itself spliced (a direct call with a literal block, or a poly dispatch arm), a bare `super` has no block node, and the code used the block currently being spliced (`g_block_id`), which is right. But for `super(&)` the call's block node is a `BlockArgumentNode`, and the code took that node as the block to splice. It isn't a block body, so each `yield` in the parent was emitted as `(void)(1LL)` and the caller's block never ran. The same happened for `super(&blk)` naming the method's own block. In the poly reproducer only the class using a bare `super` printed.

A `BlockArgumentNode` on the `super` now goes through `resolve_forwarded_block`, as an inlined `inner(&)` does. An anonymous `&`, or `&blk` naming the method's own block, resolves to the block being spliced, which is then spliced into the parent's yields. If it resolves to a real proc (`super(&PR)`, or a caller driven by `&pr`), `emit_forwarded_proc_arg` gives that proc's expression and it drives the parent's yields through `fwd_yield_proc`, the path already used when the caller holds its block as a proc. A bare `super`, a literal block on the `super` itself, and a caller with a named `&blk` that doesn't yield take the same paths as before.

Tests: `test/super_anon_block_splice.rb` is the issue's poly reproducer. `test/super_anon_block_splice_variants.rb` covers `super(&)`, bare `super`, `super(&blk)`, a three-level `super(&)` chain and `super(&PR)` with a constant proc, through direct and poly receivers, plus a caller passing `&pr`. Both fail on master and match CRuby 4.0 with this change. `make gate` is clean apart from the two known sandbox failures, `pkg.tmpdir.tmpdir_expand_usable` and `socket_ipv6_and_class_methods`.
