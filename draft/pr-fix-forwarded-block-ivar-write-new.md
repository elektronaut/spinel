title: A forwarded block reaches super from an inlined body

Fixes #N.

A method whose block is only forwarded is yield-inlined into its caller, and inside the splice the forward `&` or `&blk` stands for the caller's literal block (`g_block_id`). `resolve_forwarded_block` turns such a forward into that literal, and most call sites run it first; #4974 added it to `Klass.new`. `emit_super_block_arg` in `src/codegen.c` read the `super` call's block node raw. An anonymous `&` has no expression, so it fell through to the "no block" case and passed `NULL`, and the parent's `@handler` was nil. A named `&blk` was emitted as `lv_blk`, the inlined method's own parameter, which the splice never declares, so the C didn't compile. A bare `super` or `super()` only passed the method's own block param when the method is a real function (`!s->yields`), and otherwise passed `NULL`.

`emit_super_block_arg` now calls `resolve_forwarded_block` on the block node first, so a forward inside an inlined body materializes the spliced literal with `emit_proc_literal`. An implicit `super` in an inlined body (`s->yields` with `g_block_id >= 0`) passes the spliced block too. Everything else stays the same: a literal block, a proc value and a poly-carried proc take the same paths, a node that doesn't resolve is kept as written, and with no block at the call the stored block is still nil, not a stale one.

Tests: `test/forwarded_block_stored_new_super.rb` covers `super(&)`, `super(&blk)`, a bare `super` and `super()`, each forwarding a block that writes an ivar of the calling object, and the no-block case for a bare `super` (still nil); its `Register.new(&)` and `Register.new(&blk)` cases already pass since #4974 and stay as a guard. It fails on master and matches CRuby 4.0 with this change. The `Klass.new` half this branch also carried was the same fix as #4974 and was dropped when it was rebased onto current master; the test passes there. The gate ran before the rebase and was clean apart from the two known sandbox failures, `pkg.tmpdir.tmpdir_expand_usable` and `socket_ipv6_and_class_methods`.

Not covered: a poly receiver whose `on` forwards its block to `super` raises `super: no superclass method 'on#pf'`, because the poly dispatch arm has no `super`. That's a separate site, #N (`fix-block-forward-errors-pf-super`).
