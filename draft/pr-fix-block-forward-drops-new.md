title: Every spelling of new hands its block to a stored-block initialize

Fixes #N.

When `initialize` keeps a named `&blk` and doesn't yield, the generated `sp_X_new` takes the block as a trailing `sp_Proc *`. Each way of reaching the constructor in `src/codegen_call.c` filled that slot on its own, and most got it wrong. Bare `new(&h)` in a class method, and likewise the local-held-class, exception-subclass, leaf `self.class.new` and generic static paths, left the slot out, so the C call had too few arguments. The Class-value dispatches (zero-arg, positional, keyword/splat and boxed receiver) wrote `NULL` through `emit_ctor_block_slot` whatever the call carried; that's the `self.new(&h)` case, which built the object with no block. The positional dispatch on a Class value and the dispatch on a boxed receiver were only taken when the call had no block, so a call with arguments and a block fell through to a refusal, and `infer_poly_call` in `src/analyze_infer_recv.c` didn't type a boxed `new` with a block. Finally, the static stored-block arm read a forwarded `&h` inside an inlined method as written, which named the callee's own `lv_h`, undeclared at the site.

One helper, `emit_ctor_block_value`, now resolves the call's block the way other block-passing calls do: a literal or a forward of the inlined caller's literal through `resolve_forwarded_block` becomes a proc via `emit_proc_literal`, a proc value threads itself, a boxed proc is unboxed, and an anonymous `&` in a real function forwards that function's own block param with `emit_forwarded_proc_arg`. `emit_ctor_block_slot` takes the call node and uses it, and every static path that builds `sp_X_new(...)` now calls it; `emit_ctor_alloc_init` takes the call too, because `sp_X_initialize` has the slot. The Class-value dispatches hoist the block once into a rooted temp (`hoist_ctor_block`) that all their arms share, so a literal block isn't materialized once per class. The positional and boxed dispatches, and the analyzer's typing of a boxed `new`, now accept a block unless some class has a yielding `initialize` (`ctor_block_dispatchable`), because a yielding `initialize` has no slot and is only inlined at static sites. What stays the same: the refusal for a forwarded block of an unmodeled static type is kept, a call with no block still passes `NULL`, and a yielding `initialize` is still inlined only at static sites.

This overlaps #4974 (`fix-new-block-forwarding`) and #N (`fix-forwarded-block-ivar-write-new`), which both fixed the static stored-block arm of `emit_class_new_call` for a forward from an inlined method, and merging either with this branch conflicts in `src/codegen_call.c`. Resolve it toward this branch: `emit_ctor_block_value` does the same resolution for that arm, including the anonymous `&` case. #4974's analyzer change (counting `Klass.new(&b)` as an escape into `initialize`) is in another file and doesn't conflict.

Tests: `test/ctor_forward_block_bare_new.rb` is the issue's bare `new(&h)` reproducer and `test/ctor_forward_block_self_new.rb` is the `self.new(&h)` one. `test/ctor_forward_block_arms.rb` covers a static `K.new(&h)` in a method that gets inlined, a proc passed as `&pr`, a Class value with and without arguments, a boxed receiver read from a hash, an anonymous `&` into a Class value with an argument, and a class method's `new(n, &h)` and `self.new(3, &)`. All three fail on master and match CRuby 4.0 with this change. `make gate` is clean apart from the two known sandbox failures, `pkg.tmpdir.tmpdir_expand_usable` and `socket_ipv6_and_class_methods`.

Not covered: a constructor forward of a block that an inlined method received as a proc (`def make(&) = Reg.new(&)` spliced into a method taking `&blk`) still goes through plain `resolve_forwarded_block` in `emit_ctor_block_value`. The proc-aware resolver comes from a separate fix (#N, `fix-block-forward-drops-named-anon`), and switching this call to it is a one-line follow-up once both are merged.
