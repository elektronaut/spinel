title: An inline-only method takes its cls_id dispatch arm through its proc form

Fixes #N.

A method that yields, or whose `&blk` is used only by `.call` and `.nil?`, is marked `yields` and spliced inline at its call sites, so it has no C function. When a call dispatches on `cls_id` because a class in the hierarchy overrides the method, the switch (`emit_dispatch_per_arm` and `dispatch_arms_disagree` in `codegen_fold.c`) skipped every arm whose method has no symbol, so the inline-only override lost its arm and the `default:` ran the ancestor's method for it. The poly-receiver dispatch already solved the same problem with proc-form clones, a real function taking the block as an `sp_Proc *` (#3399), but `make_yield_proc_forms` only cloned methods whose name is called on a poly receiver (`pf_wanted`), and the `cls_id` switch never used the clones. In the mirrored case the base method is the inline-only one: `emit_inline_call_x` (`codegen_iter.c`) spliced its body at the call, so a subclass's plain override was never reached either.

`make_yield_proc_forms` (`analyze.c`) now also clones a yielding method when a class above or below it defines the same name (`pf_in_class_dispatch`), skipping `initialize`, class methods and Struct classes. In `codegen_fold.c` a new `dispatch_arm_scope` gives an arm the method itself when it has a symbol and its clone otherwise, for the per-class arms and the `default:` arm alike. Any clone arm sends the switch down the per-arm path, since a clone always takes the block, and the arm unboxes the clone's poly return when the switch fills a concrete slot. `emit_inline_call_x` declines to splice when the dispatch class has more than one implementation of the name and the method has a clone, so the call goes through the switch. Methods with a symbol keep the arms they had, and an inline-only method with no override in its hierarchy is still spliced as before.

Tests: `test/dispatch_inline_only_override.rb` is the issue's reproducer. `test/dispatch_inline_only_override_variants.rb` covers a block passed through the switch to a `&blk` override, a `yield`-based override, an inline-only base with a plain override (with and without a literal block, and through `map` over both receivers with a block reading a local), and three levels returning `Integer` on every arm, which exercises the unbox of the clone's return. Both fail on master and match CRuby 4.0 with this change. `make gate` is clean apart from the two known sandbox failures, `pkg.tmpdir.tmpdir_expand_usable` and `socket_ipv6_and_class_methods`.

Not covered: Struct classes are left out of the new clone rule. Every Struct class carries its own copy of the generated `each`/`each_pair`, so a Struct subclass always looks like an override, and cloning those bodies is refused because the clone does not carry their desugared accumulator local. A real override of a yielding method on a Struct subclass therefore still takes the parent's arm; fixing it needs clones to carry desugared locals.

Not covered either: `break` in a block given to an inline-only base that is overridden now goes through the switch and a real `sp_Proc`, and raises `break from proc-closure (LocalJumpError)` instead of returning the value. On master that call fails to compile (`void value not ignored as it ought to be`), with or without the override, so this is a separate bug that already existed; `next` in such a block works.
