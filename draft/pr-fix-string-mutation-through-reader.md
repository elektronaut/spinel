title: A String ivar mutated through its reader is the same object everywhere

Fixes #N.

A mutable String ivar that is mutated in place is stored as a shared handle (`sp_String *`), so every reader and alias sees one object; one that isn't stays a plain string, and each read is a copy. Three gaps in `src/analyze.c` let a mutation through `obj.reader` land in a copy. First, the reader-alias pass in `promote_shared_stored_strings` (#3227, `x = c.name`) only shared the handle when `strbuf_ivar_mut_kind` said the ivar's own class mutates it. When the only mutation is through the reader, the external reader-mutation pass had already promoted the ivar to a handle, but the alias was still emitted as a copy, so `x` kept `"ab"` after `c.name << "!"`. Second, that external reader-mutation pass only accepted mutators with an ivar arm (`sp_str_mutator(..., SP_MUT_IVAR)`). `c.name.slice!(0)` was therefore compiled against a copy and silently dropped, and `c.name[0] = "X"` found no arm and raised `NoMethodError` at run time. Third, `sb_mut_tabs_build` marked an ivar -1 (never promote) when its own class used `insert`, `slice!`, `[]=` or `setbyte` on it. That rule predates the #4363 shared-mutable shims, which now handle all four on an ivar, and once an ivar was marked, even a plain `c.name << "!"` through its reader was lost.

The alias pass now also accepts an ivar that is already a shared handle (`ivar_str_shared`), while still refusing one marked -1. The external pass takes every String mutator (`SP_MUT_LOCAL`). For the four with no ivar arm, codegen runs the #4363 shim over the reader call: a new `sb_call_shadow_open`/`sb_call_shadow_close` pair (`src/codegen_util.c`) overrides the call, through the `g_argov_*` table, to read a shadow copy typed as a plain String, and sets `g_sb_shadow_recv` so the arms' write-back checks treat the call as an lvalue; afterwards the shadow is written back into the handle with `sp_String_set_bin`, after a frozen check. This is wired into `sb_iv_expr_shim` (value position, `src/codegen_call_recv.c`) and `emit_array_mutate_stmt` (statement position, `src/codegen_stmt.c`). `sb_mut_tabs_build` counts `insert`, `slice!`, `[]=` and `setbyte` as ordinary mutators (1); other bang methods still mark the ivar -1. Inference needed one change: a handle-typed receiver (`TY_STRBUF`) matched none of the String rows in `infer_call`, so `setbyte`'s Integer answer was typed as a String. It is now read as a String receiver, except for the appenders that answer the receiver itself (`<<`, `concat`, `prepend`, `replace`, `insert`, `clear`), which keep the handle type because their in-place arms are chosen on it; without that exception `issue_3307_container_reader_mutation` regressed. Mutations on an ivar or a local receiver take the same paths as before; the new branches only fire for a reader call whose result is a handle.

Tests: `test/string_ivar_reader_alias.rb` is the issue's first reproducer, plus an alias surviving `[]=` and `upcase!` through the reader, a mutation of the alias reaching the ivar, and `insert` through the reader keeping `equal?` identity with the alias. `test/string_ivar_reader_mutators.rb` is the issue's second reproducer, plus `setbyte`, `slice!`, `[]=` and `insert` through the reader in value and statement position, the same four inside the class followed by `<<` and an alias through the reader, and `FrozenError` from a frozen ivar through the reader. Each section is in its own method so its receivers stay monomorphic. Both fail on master and match CRuby 4.0 with this change. `make gate` is clean apart from the two known sandbox failures, `pkg.tmpdir.tmpdir_expand_usable` and `socket_ipv6_and_class_methods`.

Not covered: a poly receiver through the reader (one local holding objects of two classes that both define `name`). On master `c.name << "!"` in that shape already fails the C build (`assignment to 'sp_String *' from incompatible pointer type 'const char *'`), because the poly reader dispatch types its result slot `const char *` while the handle demand assigns an `sp_String *`; `c.name[0] = "X"` there, which raised `NoMethodError` at run time, now fails the same way. That's the poly dispatch's own problem and needs its own fix.
