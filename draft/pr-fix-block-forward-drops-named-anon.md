title: A forward of an inlined method's proc block reaches the method it calls

Fixes #N.

`Outer#install(&blk)` keeps its block, so it's a real function with `blk` as an `sp_Proc *` local. It calls `Front#install(&) = @k.install(&)`, which only forwards its block, so that call is inlined, and the `BlockArgumentNode` branch of `emit_inline_call_x` runs the splice with no literal block (`g_block_id = -1`), recording `lv_blk` as `g_yield_proc_ref` so that a `yield` in the body calls the proc. But the body doesn't yield; it forwards `&` to `Keeper#install`, which stores the block. That forward went through `resolve_forwarded_block` (`src/codegen_fold.c`), which maps a forward to the inline's literal block, found none and answered "no block", so `Keeper#install` was called with `NULL`. Named into named worked because a named `&b` in the middle is a real `TY_PROC` local that is emitted directly.

Two helpers in `src/codegen_fold.c` handle the proc case. `forwards_inline_proc` recognizes a forward (an anonymous `&`, or `&name` naming the inline's `g_block_param_name`) made while the inline runs under a proc with no literal block. `resolve_forwarded_block_or_proc` keeps such a forward as its node instead of resolving it to nothing, and otherwise defers to `resolve_forwarded_block`; `emit_forwarded_proc_arg` then writes `g_yield_proc_ref` for it. Every site that passes a block on as a proc value now uses them: `emit_cmethod_block_arg` and `emit_method_call`, the two block-arg paths in `codegen_fold.c` (the per-arm dispatch and the method call with a block tmp), the poly-dispatch proc hoists (zero-arg and n-arg) and the class-method cascade. The last two also try `emit_forwarded_proc_arg` before `emit_proc_literal`. `resolve_forwarded_block` itself is deliberately unchanged: its other callers are the builtin-iterator splicers, which need a literal body to splice, and a forward with a literal block resolves exactly as before.

Tests: `test/block_forward_named_into_anon.rb` is the issue's reproducer. `test/block_forward_named_into_anon_arms.rb` covers named into named into anonymous (`Outer` to `Mid` to `Front`), a poly receiver in the anonymous forwarder (`Front` over two keeper classes), and a top-level anonymous forwarder called from a top-level named one. Both fail on master and match CRuby 4.0 with this change. `make gate` is clean apart from the two known sandbox failures, `pkg.tmpdir.tmpdir_expand_usable` and `socket_ipv6_and_class_methods`, and one benchmark ERR, `bm_ao_render`, whose `spinel -c` step failed or timed out under the parallel gate. It didn't reproduce on the same build: the compile takes 0.04 s, the output matches `.expected`, and `make bench` alone gives 62 pass, 0 fail, 0 error. The diff doesn't touch anything that program compiles differently.

Not covered: a builtin iterator in the forwarder (`xs.each(&)` inside such a splice) sees the same "no literal, proc present" state, since those splicers still use `resolve_forwarded_block`; driving the proc there is a separate change. A constructor forward of the inline's proc (`def make(&) = Reg.new(&)` spliced into a `&blk` method) also still misses it; `emit_ctor_block_value`, from #4992, would need to switch to `resolve_forwarded_block_or_proc`.
