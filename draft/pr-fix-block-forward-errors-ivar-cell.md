title: A block to a block-keeping method on an untyped receiver is lifted early

Fixes #N.

The yield-inlining pass in `analyze_program` decides whether a method like `install(&handler)` can be spliced at its call sites. It can't if its block escapes, and one way it escapes is a literal block that reads `handler` and becomes a real proc. To decide that, the pass asks `a_proc_create_or_lifted`, which calls `a_block_is_lifted`, which resolves the callee through `infer_type(recv)`. For `@reg.set { |v| handler.call(v) }`, `@reg` has no type yet when this pass runs, and neither does a plain local assigned from `Reg.new`. So the block counted as spliced, `install` was inlined with no storage for `handler`, and codegen, on settled types, saw that `Reg#set` keeps its block, lifted it, and referenced a `_cell_handler` that nothing declared.

The `&blk`-forward analysis a few lines above already handles a receiver it can't type by looking at every method of that name and taking the one that keeps its block. I factored that loop into `a_name_keeps_block` and added `a_block_lifted_by_callee_name`: a literal block on a call whose receiver is still `TY_UNKNOWN` (and isn't a constant, which `a_block_is_lifted` resolves without a type) counts as lifted when some method of that name keeps its block. It is used only in the inline-candidacy scan, next to `a_proc_create_or_lifted`. The forward analysis behaves as before, since it now calls the same helper. The worst an over-eager name match can do is keep a method out of line, which is always correct, and a callee that only yields still splices.

Tests: `test/block_lifted_untyped_recv.rb` has the issue's reproducer (an ivar receiver), the same shape with a local receiver, and an ivar receiver whose callee only yields, which must still splice and run the handler. It fails on master and matches CRuby 4.0 with this change. `make gate` is clean apart from the two known sandbox failures, `pkg.tmpdir.tmpdir_expand_usable` and `socket_ipv6_and_class_methods`.
