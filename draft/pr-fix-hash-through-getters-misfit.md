title: A direct ivar hash write the hash cannot hold widens it

Fixes #N.

`infer_write_types` folds each index write into the type of the container it lands in with `fold_container_evidence`. For `def c = (@c ||= {})`, the writes through the getter (`c[1] = 2`) settle `@c` as an Integer-keyed hash. The direct `@c[:s] = 3.5` then reaches the fold with a Symbol key and a Float value; the fold refuses a key the slot cannot take and returns 0, and the site `continue`d without recording anything. `@c` stayed Integer-keyed, `put_d` stored a Symbol key and a Float into it, and the C build failed on the mismatched value type. The fold can also go the other way and replace the slot's Integer key with a String key, leaving the earlier Integer-keyed writes with the wrong hash type. The getter path already handles both cases by widening the ivar to the poly-keyed hash; the direct-ivar path had no such step.

The direct-ivar path now remembers the ivar's class alongside its name. After the fold, if the target is an ivar hash that is not already `PolyPoly`, and either the fold refused a write with a known key and value type or it changed the slot's key type, the ivar widens to `TY_POLY_POLY_HASH`, `widen_ivar_hash_literals` rebuilds the literals the ivar is assigned as that variant, and the round is marked changed. This mirrors what a write through the getter already does. Pushes, splices, locals, writes that fit, and writes whose key or value type is still unknown are left to the existing fold, so hashes that were typed correctly before keep their specialized variant.

Tests: `test/ivar_hash_direct_write_misfit.rb` is the issue's reproducer, plus a class whose hash is Integer-keyed from a write through its reader and then gets a direct String-keyed write, read back with arithmetic on the Integer value. It fails on master (the first class does not compile) and matches CRuby 4.0 with this change. The second class already prints the right result on master; it guards the String-key case the new widening also takes. `make gate` is clean apart from the two known sandbox failures, `pkg.tmpdir.tmpdir_expand_usable` and `socket_ipv6_and_class_methods`.
